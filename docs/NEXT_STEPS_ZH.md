# 本轮优化后，你需要做什么

目标：尽快开始投递，并能独立演示和解释这个项目。工程验证、真实语音验证、真人评分有效性是三件不同的事。

## 现在按这个顺序做

1. **整理本轮源码并同步 GitHub**：当前本地改动尚未自动发布。提交代码后检查新的 GitHub CI 通过；不要加入 work/、.tmp/、环境文件、会话交接或私人报告。
2. **发布对应站点**：私有站更新语音界面和诊断报告，公开只读站更新演示。两站有不同受众，不能混用配置。本轮不需要改数据库结构。
3. **做一次长回答验收**：按 [转写排障与回归](VOICE_DISPLAY_DIAGNOSTICS_ZH.md) 的真人步骤核对结尾和报告。自动测试通过不代表这一步已完成。
4. **完成三分钟演示并开始投递**：运行离线 Agent 演示，能讲清 VERIFY、ABSTAIN、重放、原始证据保护和一个失败案例。真人评测持续推进，不必把投递无限推迟。

建议先用 1–2 天完成前四步，后续按下面的优先级补研究证据。

本次本地配置预检还提示缺少 `STATINTERVIEW_SCORER_ENDPOINT` 和 `STATINTERVIEW_SCORER_MODEL`。如要在本机运行语义评分，需填写同一提供商的服务地址和模型名，再运行 `npm run doctor`；若使用 DeepSeek，还必须按现有约定配置专用 `STATINTERVIEW_DEEPSEEK_API_KEY`，不能跨提供商复用密钥。离线演示无需这些配置。线上环境独立配置，本地预检不能证明线上配置缺失。

## 优先级 0：投递前完成

| 动作 | 预计投入 | 完成标准 |
| --- | --- | --- |
| 熟悉中文导读并运行离线演示 | 30–45 分钟 | 能解释 8 个回合为什么只有 7 道正式题，以及 VERIFY / ABSTAIN 为什么不更新后验 |
| 把验证后的修改同步到 GitHub，并更新公开展示站 | 一次发布 | GitHub CI 通过；网页显示 8/8 回放、3 个自适应决策；指纹与生成产物一致 |
| 用未登录窗口打开简历上的 GitHub 和公开演示链接 | 5–10 分钟 | 文档与演示可见；公开站的完整面试 API 仍被阻止 |
| 录制一段约 3 分钟演示 | 30–60 分钟 | 讲清问题、展示追问/弃权/更新、运行离线命令、解释一个失败案例；画面不含密钥或私有数据 |
| 调整简历项目描述 | 20–30 分钟 | 采用自己能解释的 3–4 条成果；把 3.83% 明确限定为合成仿真 MAE 降幅 |

## 优先级 1：补一轮新的真实语音回归

先将本轮转写界面修复部署到私有站，再新建面试，完成后提供新的报告链接供核对。不要复用历史报告判断新修复效果。

自然覆盖：百分之三十、百分之九十五、百分之零点五、百分之二十七到百分之三十三、标准误、正/负样本、PR-AUC、F1-score、LEAD、LAG、user_id。也加入正常的“样本量 95”“观察 27 到 33 天”，核对它们没有被误补成百分比。回答中保留一次 5–10 秒自然停顿。

验收时核对：

1. 原始转写没有被覆盖，评分辅助文本可展开对照。
2. 普通数字、否定与观点未被修复模型改变。
3. 停顿不会提前换题，后半段回答不会进入下一题。
4. 报告能确认是否使用语义评分，以及是否发生回退。
5. 连续回答较长的一题，核对实时文字逐段更新；换题后本题区域清空，展开“已保存转写”能看到上一轮结尾，并与报告原文一致。
6. 查看报告“转写显示与保存核对”；旧记录或缺失记录应显示“无法比较”，不能据此声称没有错误。
7. 记录等待时间和失败样本；一轮成功仅代表冒烟测试通过。

这一步需要你真实说话，自动测试无法代替。工程简历可以开始投递，同时把这项标记为待验证。

## 优先级 2：准备面试追问

在 60–90 分钟内逐项讲给别人听，卡住的地方再回到代码：

- 为什么是 Agent？观察、状态、动作、工具、反馈各是什么？
- 为什么要公共锚点与冻结岗位基线？为什么不能让背景直接影响分数？
- 后验与信息增益怎么计算？改一个效用权重，会改变哪类选题？
- 为什么不用大模型自报置信度？什么时候 VERIFY，什么时候 ABSTAIN？
- 为什么同时保留原始转写和评分辅助文本？修复错了怎么办？
- 提交中途用户暂停、请求重复、数据库失败时，如何保证状态一致？
- 指纹为何不是安全签名？合成仿真与真实效果的差别是什么？

建议用“回答中途被提前提交”的真实问题讲一次排障：现象 → 事件时间线 → 转写稳定窗口和晚到片段处理 → 回归测试 → 新真人报告核对。不要仅说“调了一下 prompt”。

## 优先级 3：投递后继续补证据

按已有协议推进，不临时改成容易通过的指标：

1. 完成 [30 次语音协议](VOICE_EVALUATION.md)，报告转写错误率、技术词正确率、恢复成功率、p50/p95 延迟及失败数。
2. 招募第二位标注者，完成 [48–72 条回答的独立双标预实验](SCORING_EVALUATION.md)，讨论分歧后冻结评分规则，再扩展正式锁定评测集。
3. 从真实会话统计转写修复、双遍评分的调用延迟、失败率、token 与成本；缺价格时保留“未定价”，不要写成零成本。

双遍模型评分不等于双人标注；自己重复标注也不算两位独立标注者。记录同意与匿名化边界，原始测试者数据不进入公开仓库。

## 后续代码优化顺序

| 优化 | 为什么有价值 | 先决条件 |
| --- | --- | --- |
| 分阶段统计转写修复的延迟、失败、token 与成本 | 分清额外一次修复调用的收益和等待代价 | 先有新版本真实报告，明确现有埋点覆盖缺口 |
| 将语音模块按需加载并测量首屏体积 | 构建仍有大 bundle 提示；需要实测拆包收益 | 独立任务测量文本与语音首屏，避免破坏连接恢复 |
| 扩展跨语言端到端策略一致性 | 当前 golden fixtures 主要验证数学公式 | 明确哪一端拥有会话策略，冻结共同契约 |
| 增加用户身份、资源归属、删除与保留规则 | 为多人公开测试提供权限边界 | 在开放完整面试 API 前完成；当前继续 owner-only |

这些改进各有验收目标。投递前优先保证示例能跑、问题能解释、证据可信；不要为了堆技术名词加入新的框架或服务。
